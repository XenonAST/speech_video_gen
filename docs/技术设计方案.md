> 版本：**v2.0（单机离线版）**
> 日期：2026-09-26
> 作者：AI 算法开发工程师
> 状态：设计评审稿
>
> **v2.0 变更摘要**：根据新增的两条约束（① 全离线单机部署、仅本人使用、无商用计划；② 单卡 RTX 4090 24GB）全面重写。许可证章节从最大的风险源变为几乎无约束；架构从分布式集群坍缩为单机串行；工作量从 5–7 个月降至 **2–3 个月**。详见 [0. 约束变更影响](#0-约束变更影响v20-核心)。

## 0. 约束变更影响（v2.0 核心）

### 0.1 两条新约束

| # | 约束 | 影响面 |
|---|---|---|
| **C1** | **全离线、单机部署、仅本人使用、不商用、不分发** | 许可证约束几乎全部解除；删除所有云 API 依赖；删除多租户/计费/权限系统 |
| **C2** | **单卡 RTX 4090 24GB 家用电脑** | 架构从"分布式并行"坍缩为"单卡串行 + 模型换入换出"；并发模型全部失效；显存预算成为设计核心 |

### 0.2 三句话结论

1. **C1 是本方案最大的简化。** GPL-3.0 的义务只在**分发**时触发——自用不分发则**零义务**。这意味着 **ComfyUI（GPL-3.0）可以直接作为推理引擎**，原本需要自研的整套模型服务化、任务编排、显存管理工作几乎全部省掉。同理，RVM、CodeFormer、LongCat-Video-Avatar（原本因商用限制被排除）现在全部可用。
2. **C2 的主要代价是"串行"而非"跑不动"。** 所有关键模型都能塞进 24GB（LatentSync 1.6 需 18GB，是最大的一块）。但同一时刻**只能跑一个**，因此设计的核心从"并行调度"变成**"如何用批处理减少模型换入换出次数"**。
3. **工作量从 5–7 个月降至 2–3 个月（1 人）。** 删掉的有：多租户、配额计费、K8s 集群、监控告警、权限体系、前端工程化。保留的是：素材入库、工作流搭建、Python 胶水层。

### 0.3 一句话提醒

> ⚠️ **"个人自用"解除的是软件许可义务，不解除内容合规义务。** 如果生成的视频要发到 B站/抖音/视频号，平台侧仍然要求 AI 生成内容标识。这一条不能省，见 [第 10 章](#10-合规个人使用版)。

## 1. 产品定位（修订）

### 1.1 一句话定义

一套**完全离线运行于单台 4090 家用电脑**的 AI 数字人视频生产工具：本人一次性提供视频素材与音频素材完成形象与声音克隆，此后仅需输入文案，即可批量生成**本人的口播视频**与**讲课视频**。

### 1.2 核心价值（修订：从商业价值改为个人价值）

| 维度 | v1（商业版） | **v2（个人版）** |
|---|---|---|
| 隐私 | 私有化部署 | **物理隔离，素材永不出本机** |
| 成本 | 摊薄 SaaS 分钟费 | **零边际成本**（电费外） |
| 质量上限 | 受许可证约束的选型 | **可用最强模型，无约束** |
| 批量 | 多用户并发 | **挂机批处理，一夜出片** |
| 合规 | 平台级义务 | 仅内容标识义务 |

### 1.3 明确不做（v2 范围外）

- ❌ 实时交互 / 直播数字人（技术栈不同，见 [4.4.5](#445-实时流式方案备选赛道)）
- ❌ 换脸到他人视频
- ❌ 多用户 / 账号体系 / 计费
- ❌ 移动端、云部署

## 2. 场景定义（不变）

### 2.1 三种内容形态

**A. 口播视频** — 15 秒–5 分钟，数字人半身/特写，可叠字幕、BGM
**B. 讲课视频** — 5–60 分钟，PPT 为主体，数字人画中画讲解
**C. 全屏长视频** — 5–30 分钟，数字人全屏讲解（难度最高，列 v2 之后）

### 2.2 输入输出契约

```
输入：
  ├── video_refs:   视频素材（建议总时长 ≥ 5 分钟，最佳 ≥ 30 分钟正面素材）
  ├── audio_refs:   音频素材（建议 ≥ 10 秒，最佳 3~10 分钟干净人声）
  ├── script:       文案
  ├── presentation: 课件（可选，PPTX/PDF）
  └── params:       分辨率、画幅、语速、字幕后处理、BGM

输出：
  ├── video:        成片 MP4（H.264, 1080P, 25fps, AAC）
  └── subtitle:     SRT
```

### 2.3 两条质量档位

| 档位 | 技术路线 | 单卡 4090 可行性 | 适用 |
|---|---|---|---|
| **标准档**（生成式） | 唇形驱动扩散模型重绘嘴部 | ✅ LatentSync 1.6 需 18GB，独占运行 | 默认档 |
| **极速档**（检索拼接） | 素材库检索音素匹配片段拼接 | ✅ 几乎不占显存，秒级 | 草稿预览、批量 |

> 极速档在单卡环境下价值更高：**它几乎不消耗 GPU**，可以在不打断大模型任务的情况下随时出片。

## 3. 技术选型总原则（修订）

原 v1 的四条原则中，第 1 条"许可证优先"在 C1 下**完全失效**，替换为两条新原则：

1. ~~许可证优先于效果~~ → **在自用场景下，选效果最好的**。唯一的例外是内容合规（第 10 章）。
2. **不训练模型，只做集成与微调。** 开源生态已覆盖 90% 需求。
3. **所有重模型串行执行，用批处理摊薄换入换出开销。**（C2 带来的新原则，单卡环境的核心纪律）
4. **ComfyUI 作推理引擎，Python 做业务编排。**（C1 解锁的新架构，见 [4.7](#47-编排层comfyui-作引擎-python-作编排)）
5. **全程可断点续跑。** 单机跑长视频动辄数小时，任何一步崩溃都不能从头再来。

### 4.2 语音合成与声音克隆（模块 ③）

#### 选型对比（许可证列已按自用场景重新评估）

| 模型 | 许可证 | 中文效果 | 显存 | 推荐度 |
|---|---|---|---|---|
| **IndexTTS2** | Apache-2.0 | CER 1.03 / SS 76.5，**情感相似度 0.872**，token 级时长控制 | FP16 约 7.8GB | ⭐⭐⭐⭐⭐ **首选** |
| **CosyVoice 3** | Apache-2.0 | CER 1.21 / SS 78.0，18+ 中文方言 | 4–8GB | ⭐⭐⭐⭐⭐ **并列首选** |
| **GPT-SoVITS** | MIT | 中文社区克隆最强，**少样本微调** | 6GB+ | ⭐⭐⭐⭐⭐ **音色保真度天花板** |
| F5-TTS | MIT | 轻量，无情感控制 | ~3GB | ⭐⭐⭐ |
| Fish Speech 1.5 / S2-Pro | Apache-2.0 / **Research License** | 多语言 80+ | 4–8GB+ | ⭐⭐⭐ **自用下 S2-Pro 已可用** |
| ~~MiniMax speech-02 API~~ | 商业 | ~~99% 克隆准确率~~ | 无需 GPU | ❌ **C1 排除（需联网）** |

#### 推荐方案：**分层策略**

```
音色保真度优先级（个人使用的核心诉求）：
  ┌─ 若提供 ≥ 1 分钟干净音频 → GPT-SoVITS 微调专属模型  ★最高保真
  ├─ 若提供 10 秒–1 分钟      → IndexTTS2 零样本克隆    ★次高
  └─ 兜底                    → CosyVoice3 零样本        ★够用
```

**为什么把 GPT-SoVITS 提为首选（相比 v1 的重要变化）：**
- v1 中它排第三，因为"商用需考虑训练成本与合规"。C1 下这个顾虑消失。
- 个人使用**只克隆一个音色**，微调是一次性投入（约 30 分钟 GPU 时间），此后所有生成都受益
- 少样本微调的音色相似度**显著优于任何零样本方案**，而音色相似度恰恰是数字人产品最影响观感的指标

**显存与共存：**
- IndexTTS2 (7.8GB) 和 CosyVoice3 (4–8GB) **不能同时常驻**，需二选一或换入换出
- GPT-SoVITS 推理时约 6GB，可与对齐模型共存

#### 工程要点（C1 下的变化）

```python
# 伪代码：TTS 批处理调度（单卡核心模式）
def synthesize_batch(all_sentences: List[Segment]) -> List[Audio]:
    """
    关键：模型只加载一次，处理完所有句子再卸载。
    若逐句加载/卸载，4090 上单次加载 CosyVoice3 约 10-20 秒，
    100 句话就是 30+ 分钟的纯浪费。
    """
    with model_scope("cosyvoice3", vram=8):   # 进入时加载，退出时卸载
        audios = [tts.synthesize(s) for s in all_sentences]
    return audios
```

> ⚠️ **关键工程坑**：长文本一次性喂给 TTS 会导致韵律漂移和"念经感"。必须**分句合成再拼接**，并在句间保留自然停顿（逗号 200ms / 句号 400ms / 段落 800ms）。

### 4.3 文本处理与本地 LLM（模块 ②，v2 新增重点）

**C1 带来的最大功能缺口**：v1 用云端 LLM 做口语化改写、分句、多音字消歧——**离线环境下必须本地化**。

#### 本地 LLM 选型（24GB 单卡约束下）

| 模型 | 量化 | 显存 | 能力 | 推荐度 |
|---|---|---|---|---|
| **Qwen3-14B** | Q4_K_M / AWQ | ~10–11GB | 口语化改写、分句、消歧质量好 | ⭐⭐⭐⭐⭐ **首选** |
| Qwen3-8B | Q4 | ~6GB | 够用，速度更快 | ⭐⭐⭐⭐ 备选 |
| Qwen3-4B | Q4 | ~3GB | 可与其他模型共存 | ⭐⭐⭐ 轻量 |

**运行方式二选一：**

| 方式 | 优势 | 劣势 |
|---|---|---|
| **Ollama / llama.cpp（CPU 推理）** | ✅ **完全不占显存**，可与 GPU 任务并行 | 慢（14B Q4 约 5–10 token/s，处理一千字文案约 1–3 分钟） |
| GPU 推理（vLLM / llama.cpp CUDA） | 快 | 需从 LatentSync 抢显存，必须换入换出 |

**推荐：CPU 推理**。文案处理是一次性、非实时的操作，5 分钟等待完全可接受；而**不占用显存**这一点在单卡环境下价值极高——可以在 GPU 跑唇形驱动的同时，用 CPU 处理下一批文案。

#### 除 LLM 外必需的传统 NLP 工具（离线）

| 任务 | 工具 | 说明 |
|---|---|---|
| 数字/日期/单位归一化 | `cn2an` / `number_normalizer` | "2026年" → "二零二六年" |
| 多音字消歧 | `pypinyin` + 自定义词典 + LLM 兜底 | "银行/行走"、"重庆/重复" |
| 分句 | `pysbd` / 自研规则 | 中文分句需处理引号、括号嵌套 |
| 敏感词/合规检查 | 本地词库 | 离线环境无云端审核 |

**多音字问题的工程解法：**
```python
# 三级处理，逐级兜底
def resolve_polyphone(text: str) -> str:
    # L1: 词典精确匹配（覆盖 95% 高频词，零成本）
    #     "银行"→yínháng, "重庆"→chóngqìng, "重复"→chóngfù
    if hit := polyphone_dict.match(text):
        return hit
    # L2: 词性/上下文规则（覆盖 4%）
    if hit := rule_engine.resolve(text):
        return hit
    # L3: 本地 LLM 消歧（覆盖剩余 1%，cost 可接受）
    return llm_disambiguate(text)
```
**并且提供人工干预入口**：允许在文案中直接标注拼音 `重[chóng]庆`，绕过所有自动逻辑。

### 4.4 语音识别与强制对齐（模块 ④）

#### 选型（离线可用性已确认）

| 工具 | 许可证 | 显存 | 定位 |
|---|---|---|---|
| **Qwen3-ForcedAligner-0.6B** | Apache-2.0 | ~2GB | ⭐⭐⭐⭐⭐ **强制对齐首选**（11 语言，非自回归，1000 秒音频约 1 秒；官方称精度超 WhisperX / NeMo-FA） |
| **FunASR (Paraformer-large + fsmn-vad + ct-punc)** | MIT | 4–8GB | ⭐⭐⭐⭐⭐ **ASR / 素材入库首选**（中文工业级） |
| WhisperX | BSD-2 | 4GB | ⭐⭐⭐ 备选（中文需外挂 wav2vec2 XLSR；长句 backtrack 有已知失败） |

**双引擎分工：**
- **有已知文案** → Qwen3-ForcedAligner（**本项目 90% 的场景**）
- **无文案（素材入库时反查音素）** → FunASR

> ⚠️ **常见技术选型错误**：用 ASR 去做对齐。"已知文案求时间戳"是**强制对齐（Forced Alignment）**问题，不是 ASR 问题，精度差异显著。
>
> ⚠️ **模型常驻**：0.6B 模型仅占 2GB，**建议常驻显存**，避免反复加载。

### 4.5 数字人形象生成（模块 ⑤⑥）★核心★

#### 4.5.0 四类任务必须严格区分

| 任务 | 输入 | 输出 | 代表模型 | 本产品用途 |
|---|---|---|---|---|
| **① 口型替换 / 配音** | 已有视频 + 新音频 | 保留原背景，仅重绘嘴部 | LatentSync, MuseTalk | ✅ **主线** |
| **② 肖像动画** | 单张图 + 音频 | 从静态图生成说话视频 | EchoMimic, Hallo3 | ✅ 辅助 |
| **③ 说话视频生成** | 图/视频 + 音频 | 重新生成整帧 | InfiniteTalk | ✅ 增强 |
| **④ 通用视频生成** | 文本/图/参考 | 任意视频 | MiniMax H3 | ✅ 补镜头 |

> **混淆 ①②③④ 是选型失败的头号原因。** 拿"肖像动画"模型做"口播配音"，结果必然是身份漂移。

---

#### 4.5.1 口型驱动模型对比（任务①，主线）

| 模型 | 许可证 | **显存** | 4090 可行性 | 效果 | 推荐度 |
|---|---|---|---|---|---|
| **LatentSync 1.6** | Apache-2.0 | **18 GB** | ✅ **可跑，但独占 24GB 卡** | 口型精度最高，AV offset 近零；**v1.5 起含中文训练数据**；已知 issue #67 输出轻微模糊 | ⭐⭐⭐⭐⭐ **画质主线** |
| **LatentSync 1.5** | Apache-2.0 | **8 GB** | ✅ 宽裕，可与小模型共存 | 略逊 1.6 | ⭐⭐⭐⭐⭐ **速度主线** |
| **MuseTalk 1.5** | MIT | 4–8 GB | ✅ 轻松 | 工作区 256×256；有嘴部抖动/模糊反馈 | ⭐⭐⭐⭐ 快速预览档 |
| **LongCat-Video-Avatar 1.5** | MIT 权重 + 伦理声明**禁商用** | 中 | ✅ | 8 步蒸馏（**8 NFE**）；Whisper-large-v3 多语种口型；**滚动推理保持长视频身份一致** | ⭐⭐⭐⭐⭐ **C1 解锁的新选项** |
| KeySync | 需核实 | 中 | ✅ | 针对表情泄漏与遮挡优化 | ⭐⭐⭐ 备选 |
| ~~Wav2Lip~~ | LRS2 数据禁商用 | 2GB | ✅ | 效果已过时，嘴部方块明显 | ❌ **不推荐**（自用虽合法，质量不值） |

#### 推荐方案：**LatentSync 1.6（画质） + LatentSync 1.5（速度）双档**

```
用户提交任务
   ├─ 立即用 LatentSync 1.5 生成预览（8GB，速度快，可与后处理模型共存）
   │     ↓ 确认口型/节奏 OK
   └─ 排队 LatentSync 1.6 生成正式成片（18GB，独占，慢但质量最好）
```

**重要变化（相比 v1）：LongCat-Video-Avatar 1.5 进入候选。**
v1 因"伦理声明禁止商用"将其排除；C1 下禁令不再适用。它的**滚动推理（rolling inference）保持长视频身份一致性**特性，恰好是 [7.1 长视频漂移](#71-长视频口型漂移) 问题的原生解法。**建议在 P0 阶段与 LatentSync 做 A/B 对比**。

**部署硬性要求：**
- **25fps 源视频 + 16kHz 音频**（LatentSync 硬性要求），预处理阶段统一转码

### 5.3 ★核心设计★ 阶段式批处理调度器

**问题**：假设要生成 10 条视频，每条 5 个分段。若按"任务流水线"逐个处理：
```
任务1: 加载LLM→卸载→加载TTS→卸载→加载对齐→卸载→加载LatentSync→卸载...
任务2: 加载LLM→卸载→加载TTS→卸载→ ... （重复 10 次）
→ 模型加载次数 = 10 任务 × 5 阶段 = 50 次
→ 每次加载 20 秒 → 纯浪费 1000 秒（16 分钟）
```

**解法：阶段式批处理（Stage-batched Pipeline）**
```
阶段1: 【加载 LLM】处理全部 10 条文案 → 【卸载】
阶段2: 【加载 TTS】合成全部音频       → 【卸载】
阶段3: 【加载 Aligner】对齐全部音频    → 保持常驻
阶段4: 【加载 LatentSync】驱动全部分段 → 【卸载】
阶段5: 【加载 GPEN/ESRGAN】后处理全部  → 【卸载】
阶段6: 【CPU】合成全部成片
→ 模型加载次数 = 5 次（与任务数无关）
→ 纯浪费从 1000 秒降到 100 秒
```

**伪代码：**
```python
class StageBatchedScheduler:
    """
    单卡串行环境的核心调度器。
    原则：模型加载次数 = O(阶段数)，而非 O(任务数)。
    """
    def run(self, tasks: List[Task]):
        # ── Stage 1: 文本处理（CPU LLM，不占显存，可与上一批 GPU 任务重叠）──
        for t in tasks:
            t.script = self.llm.rewrite_oral(t.script)
            t.segments = split_sentences(t.script, max_chars=50)

        # ── Stage 2: TTS（模型加载一次，处理全部）──
        with self.gpu.model_scope("tts", vram=8):
            for t in tasks:
                t.audio = [self.tts.synth(s) for s in t.segments]
                t.audio = concat_with_pauses(t.audio)

        # ── Stage 3: 强制对齐（小模型，常驻）──
        for t in tasks:
            t.word_ts = self.aligner.align(t.audio, t.script)
            t.chunks = chunk_by_semantic_boundary(t.audio, t.word_ts, max_dur=15.0)

        # ── Stage 4: 唇形驱动（最耗显存，集中处理全部分段）──
        all_chunks = [(t, c) for t in tasks for c in t.chunks]
        with self.gpu.model_scope("latentsync_16", vram=18, evict_resident=True):
            for t, c in all_chunks:
                c.output = self.lipsync.drive(c.base_video, c.audio)
                self.checkpoint.save(t, c)          # ★ 断点续跑

        # ── Stage 5: 后处理 ──
        with self.gpu.model_scope("postprocess", vram=12):
            for t in tasks:
                t.video = self.postprocess(t)

        # ── Stage 6: 合成（纯 CPU）──
        for t in tasks:
            self.compose(t)
```

**这个设计带来的三个好处：**
1. **模型加载次数从 O(任务数×阶段数) 降到 O(阶段数)**
2. **断点续跑粒度细**：某个分段失败只需重跑该分段，而非整条视频
3. **CPU/GPU 可重叠**：CPU 上跑 LLM 处理下一批文案时，GPU 正在跑上一批的唇形驱动

### 5.4 断点续跑状态机

单机跑长视频动辄数小时，**必须能断点续跑**。用 SQLite（无需服务端）：

```sql
CREATE TABLE task_stage (
    task_id     TEXT,
    stage       TEXT,        -- llm | tts | align | lipsync | post | compose
    chunk_idx   INTEGER,     -- 分段索引（NULL 表示整任务级）
    status      TEXT,        -- pending | running | done | failed
    output_path TEXT,        -- 中间产物路径 ★关键★
    gpu_seconds REAL,
    error       TEXT,
    updated_at  TIMESTAMP,
    PRIMARY KEY (task_id, stage, chunk_idx)
);
```

**核心规则：每个 stage 的输出都落盘。** 改字幕样式不该重跑唇形驱动；换 BGM 不该重跑 TTS。

## 6. 核心流程详细设计

### 6.1 素材入库流程（一次性，决定最终效果上限）

```
用户提供视频素材
    │
    ▼
[1] 转码标准化
    ffmpeg → H.264 / 25fps / 统一分辨率 / 音频 16kHz 单声道
    │
    ▼
[2] 场景切分 (PySceneDetect) → 独立镜头，剔除转场帧
    │
    ▼
[3] 人脸检测与跟踪 (InsightFace)
    ├─ 过滤：多人场景、遮挡 >30%、侧脸 >45°、模糊（Laplacian 方差阈值）
    ├─ 跟踪：按人脸 ID 分组，保留主体
    └─ 关键点：对齐到标准正脸模板
    │
    ▼
[4] 质量打分（每段 0–100）
    score = w1·清晰度 + w2·光照均匀度 + w3·正脸度 + w4·分辨率 + w5·表情中性度
    │
    ▼
[5] 音素级切分 ★关键★
    FunASR 对素材音轨做 ASR → 音素级时间戳
    按音素边界切分视频 → 建立「音素 n-gram → 视频片段」倒排索引
    │
    ▼
[6] 建索引
    维度：音素序列 / 语速 / 音高 / 景别 / 头部姿态 / 表情 / 时长 / 质量分
    │
    ▼
[7] 输出资产
    ├─ clip_library.json   （检索索引，供极速档使用）
    ├─ face_embedding      （身份一致性基准）
    ├─ base_clip.mp4       （最佳"中性基座"片段）
    └─ quality_report.md   （★反馈给用户：素材哪里可以改进）
```

**产品化亮点：素材质量报告。** 入库后生成报告："您的素材 62% 可用，主要问题是侧脸过多（建议补拍正面），预计成片质量 4/5 星"。这直接决定最终效果，是**个人使用场景下最有价值的反馈**。

### 6.2 口播视频生成流程

```python
async def generate_oral_video(task: Task):
    # ── Stage 1: 文本处理（CPU LLM，不占显存）──
    script = await llm.rewrite(task.script, style="oral")     # 口语化改写
    segments = split_sentences(script, max_chars=50)
    segments = resolve_polyphone(segments)                    # 多音字消歧

    # ── Stage 2: TTS ──
    audios = [tts.synthesize(s, task.voice_id) for s in segments]   # 串行，模型常驻
    audio = concat_with_pauses(audios, pauses=[200, 400, 800])
    audio = loudness_normalize(audio, target_lufs=-16)

    # ── Stage 3: 强制对齐 ──
    word_ts = await forced_align(audio, script)
    subtitle = build_srt(word_ts)

    # ── Stage 4: 语义分段（长视频不漂移的关键）──
    chunks = chunk_by_semantic_boundary(audio, word_ts, max_dur=15.0)

    # ── Stage 5: 基座视频准备 ──
    base_clips = []
    for i, chunk in enumerate(chunks):
        clip = (await retrieve_from_library(chunk, task.avatar_id)  # 素材库检索
                or default_base_clip(task.avatar_id, chunk.duration))  # 中性基座
        base_clips.append(clip)

    # ── Stage 6: 唇形驱动（GPU 密集，串行）──
    driven = [lipsync.drive(bc, c) for bc, c in zip(base_clips, chunks)]

    # ── Stage 7: 段间拼接 ──
    video = stitch_with_crossfade(driven, overlap_frames=4)
    video = enforce_color_consistency(video, ref_frame=driven[0].frame(0))

    # ── Stage 8: 后处理 ──
    video = await face_restore(video)     # GPEN
    video = await upscale(video)          # Real-ESRGAN（如需要）

    # ── Stage 9: 合成包装（CPU）──
    return compose(video, subtitle=subtitle, bgm=task.params.bgm,
                   intro=..., outro=..., ai_label=True)
```

### 6.3 讲课视频生成流程（单卡版：并行 → 阶段批处理）

**v1 中"按 PPT 页并行"的设计在单卡上失效**，改为：

```
输入：PPTX 课件 + 讲稿（或由本地 LLM 从课件生成讲稿）

┌─ 步骤 1：课件解析（CPU）──────────────────────────┐
│  python-pptx 解析：每页文本、图片、备注、图表       │
│  LibreOffice headless 渲染每页为 PNG（保真度最高）  │
│  提取每页要点摘要用于讲稿生成                       │
└──────────────────┬───────────────────────────────┘
                   ▼
┌─ 步骤 2：讲稿生成（CPU LLM，一次性处理所有页）─────┐
│  按页生成讲稿，控制每页时长                         │
│  IndexTTS2 的 token 级时长控制在此发力              │
│  生成转场语："接下来我们看第二页……"                │
└──────────────────┬───────────────────────────────┘
                   ▼
┌─ 步骤 3：TTS 批处理（模型加载一次，合成全部页）─────┐
└──────────────────┬───────────────────────────────┘
                   ▼
┌─ 步骤 4：唇形驱动批处理（模型加载一次，处理全部段）─┐
│  ★ 这是最耗时的一步，也是断点续跑最关键的一步        │
│  每页独立成段 → 失败只重跑该页                      │
└──────────────────┬───────────────────────────────┘
                   ▼
┌─ 步骤 5：抠像（BiRefNet 常驻）→ 透明背景 ──────────┐
└──────────────────┬───────────────────────────────┘
                   ▼
┌─ 步骤 6：逐页合成（CPU，可与其他 GPU 任务重叠）────┐
│  背景 = PPT 渲染图                                 │
│  前景 = 数字人（画中画，位置/大小可配置）            │
│  叠加 = 字幕 + 页码 + 进度条 + 要点高亮             │
└──────────────────┬───────────────────────────────┘
                   ▼
┌─ 步骤 7：长视频拼接（CPU）─────────────────────────┐
│  按页 concat，统一编码参数                          │
│  可选：章节标记（MP4 chapters）                     │
└────────────────────────────────────────────────────┘
```

**讲课模式在单卡环境下的两个巨大利好：**
1. **数字人只占画面一角**，PPT 遮挡大部分画面 → 数字人分辨率可降到 512×512 就够，**算力大幅节省**
2. **一致性压力小** — 数字人区域小、动作幅度小，漂移不易察觉

**因此：讲课模式的实现难度显著低于全屏长视频，应作为 v2 的第二个交付形态。**

## 7. 关键技术难点与解决方案

### 7.1 长视频口型漂移

**问题**：直接把 10 分钟音频喂给唇形驱动模型，输出会出现面部色彩漂移、身份退化、口型逐渐失步。

**四层防护：**
```python
def ensure_consistency(segments, ref_embedding, threshold=0.65):
    """第 4 层：身份一致性自动校验"""
    for i, seg in enumerate(segments):
        emb = insightface.extract_id(seg.first_frame)
        sim = cosine(emb, ref_embedding)
        if sim < threshold:
            segments[i] = regenerate(seg, seed=SEED_FIXED)   # 固定种子重跑
    return segments
```

1. **语义分段**：按标点 + 静音边界切成 10–20 秒段，段内独立生成
2. **基座锚定**：每段使用**同一段基座视频**，避免身份基准漂移
3. **色彩锁定**：以第一段平均色彩直方图为参考，对后续段做 color transfer
4. **一致性校验**：InsightFace 提取 ID embedding，余弦相似度低于阈值自动重跑

> **新增选项**：LongCat-Video-Avatar 1.5 的**滚动推理**是这一问题的方法级解法（见 [4.5.1](#451-口型驱动模型对比任务主线)），建议在 P0 阶段对比验证。

### 7.2 口型-音频同步漂移

**问题**：源视频 25fps、音频 16kHz，帧率/采样率不匹配导致累积偏移，10 分钟后可能差几百毫秒。

**解决方案：**
- 全流程**统一时间基准**：中间产物用**帧号**而非秒（整数运算无累积误差）
- 生成：`frame_index = round(phoneme_start_time * fps)`
- 拼接：检查每段音频样本数与视频帧数是否匹配，不匹配则微调该段时长（±2 帧内，听感无影响）

> ⚠️ InfiniteTalk 存在硬编码 25fps 导致的音画漂移；**务必用 PainterNodes 的 `PainterAI2V` 修复版节点**。

### 7.3 素材不足时的基座策略

**问题**：素材可能只有 1 分钟，但要生成 5 分钟视频。

**按优先级：**
1. **素材足够** → 按文案语境检索最匹配片段（打招呼用"挥手"段，强调用"手势"段）
2. **素材一般** → "中性基座"循环 + **Idle 微动**（呼吸、眨眼、轻微头部摆动）打散循环感
3. **素材不足** → 提取首尾帧，用 H3 做首尾帧插值延长（≤15s/次）
4. **兜底** → 静态图 + InfiniteTalk 生成（形象一致性下降，需明确告知）

**循环点处理**：不要简单重复，在循环点做**交叉淡化 + 音频连续**，并确保循环点落在静音处。

### 7.4 单卡 OOM 的预防

单卡环境最怕跑到一半 OOM。三重防护：
```python
def model_scope(name, vram_required, evict_resident=False):
    """显存作用域：进入时加载，退出时卸载"""
    if evict_resident:
        release_resident_models()          # 卸载常驻小模型
    free = query_free_vram()
    if free < vram_required * 1.15:        # 15% 安全余量
        torch.cuda.empty_cache()
        free = query_free_vram()
        if free < vram_required * 1.15:
            raise InsufficientVRAM(f"需要 {vram_required}GB，仅剩 {free}GB")
    yield load_model(name)
    unload_model(name)
```
1. **预检**：加载前查询可用显存，需 15% 安全余量
2. **可卸载常驻**：大模型进场时自动卸载小模型
3. **分段粒度**：每段处理完立即落盘并释放，避免累积

### 7.5 运行时长预估与心理预期管理

**单卡 4090 的耗时量级**（**必须实测标定，下表为量级参考**）：

| 任务 | 估计耗时 | 说明 |
|---|---|---|

## 附：给决策层的三条核心建议（v2）

1. **C1 解锁了最大的简化：用 ComfyUI 当推理引擎。** GPL-3.0 的义务只在分发时触发，自己用完全没问题。这省掉了整套模型服务化与显存管理的自研工作——代码量从 ~15000 行降到 ~3300 行。

2. **单卡 4090 的瓶颈是"串行"，不是"跑不动"。** 所有关键模型都塞得进 24GB（LatentSync 1.6 的 18GB 是最大的）。真正的设计重点是 [5.3 阶段批处理调度器](#53-核心设计阶段式批处理调度器)——把模型加载次数从 O(任务数×阶段数) 降到 O(阶段数)。这是本项目唯一真正有技术含量的自研部分。

3. **P0 只需 1 周，但必须用自己的真实素材。** 这是整个项目最大的风险控制点。三个验收问题：耗时多少？音色几分？口型能不能发布？答案不理想就换路线（LongCat-Video-Avatar / InfiniteTalk / HeyGem），而不是硬啃。
